## 0. 最重要ルール（安全）

ユーザは過去に何度も次を明言している。**必ず守ること。**

1. **メモリ / GPU の逼迫を避ける。** 学習・デコードは重い。実行前に必ず `free -g` と `nvidia-smi` を確認し、**すでに他のジョブが GPU を使っている時は同時に走らせない**。RAM が 90% を超えそうなら止める。
2. **`sudo` は使えない。**
3. **既存の学習済み exp を勝手に消さない。** 同名ディレクトリに上書きしそうな時は退避（`mv ..._oldXXX`）してから。
4. **長時間ジョブ（学習）はユーザが tmux で自分で回す。** AI 側は「準備・評価・集計・図表化」を担当する。学習の実行コマンドを渡し、完了報告を待って評価する、という分担。
5. 変更を加えたら、**ユニットテストで恒等性・勾配・数値を確認**してから本番に回す（後述の検証パターン参照）。

## 1. タスクと全体設計

**タスク**: 各発話に発話区間末タグ（3クラス）を予測する。
- `<継続>`（まだ言い終えていない）/ `<完了>`（言い終えた）/ `<相槌>`（短い応答）
- これは **VAD/VAP ではなく、発話内容の意味に基づく判定**。
- 評価: eval セット 23,444 区間。指標は クラス別F1・macro-F1・継続/完了の二値分離acc・ASRのCER。

**2段構成**
- **Stage1**: 現発話のみで純粋 ASR（Transducer）を学習 → エンコーダ完成。
  - タグ: `20260713-pureasr`（`exp/asr_20260713-pureasr`）。CER 23.3。**2 節までの全 Stage2 はこれを init_param に使っている。**
  - **新候補（2026-09-24）**: `20260921-pureasr-blk42-sp`（`exp/asr_20260921-pureasr-blk42-sp`）。
    **CER 20.7 / WER 27.4**。`block_size` を 18 → 42 に増やして左文脈を 0.40 秒 → 1.19 秒に伸ばし、
    さらに speed perturbation を足したもの。`look_ahead` は据え置きなので**レイテンシ 100 ms は不変**。
    詳細は `docs/stage1_asr_improvement.md`。
  - **2026-09-30: この新 Stage1 で Stage2（`frame2`）を作り直し、効果を確認した。**
    融合 macro-F1 0.7429 → 0.7537。→ §2.6。**新規の Stage2 実験はこちらを使うこと。**
  - ⚠ **`block_size` が変わるので、乗り換えると Stage2 は全部やり直し。**
    2 節・2.5 節の数値はすべて `block_size: 18` 前提であり、そのままでは比較できない。
    Stage2 の config 側の `block_size` も 42 に揃える必要がある
    （`batch_bins` と `valid_batch_bins` の注意は §2.6 末尾）。
- **Stage2**: Stage1 のエンコーダを**凍結**し、タグ予測に必要な部分だけ学習。
  - モデル: `espnet2/asr/espnet_model_turntaking_xfmr.py`（`model: turntaking_xfmr`、`espnet2/tasks/asr.py` に登録済み）
  - エンコーダ: Contextual Block Conformer（12ブロック、output_size 256）
  - ヘッド: `[過去max-poolベクトル v1..vN ; 現発話フレーム c1..cT]` を **Self-Attention 1層** に通し、**現発話の最終フレーム位置 c'_T** を MLP へ。
  - **損失は `loss = loss_tag` のみ**（ASR 損失は計算しない）。

**Stage2 の3つの重要な設計制約**（壊すと破綻する）:
1. `freeze_param: frontend / normalize / encoder / decoder / joint_network / ctc` で ASR 部分を凍結。
2. モデルの `train()` を override して、凍結部を常に `.eval()` に固定（BatchNorm の running 統計ドリフトを止める）。
3. `init_param` に Stage1 の `valid.loss.ave.pth` を指定 → **エンコーダ等のパラメータ名が Stage1 と一致している必要がある**（後述の Adapter 実装が hook 方式なのはこのため）。

## 2. これまでの実験と結論（済み）

### 済んだこと
| カテゴリ | 内容 |
|---|---|
| 過去発話（凍結） | N=0〜5、同一話者(same)/複数話者(session) |
| LoRA | N=0〜5、same/session |
| Adapter | 適応強さ s の掃引（N=0）→ s=0.4 採用 → N=0〜5、same/session |

### 確定した結論（新実験の前提として重要）
1. **過去発話は3手法すべてで有害。** 凍結・LoRA・Adapter のどれでも N=0（過去なし）が最良で、N を足すほど macro-F1 が単調低下。主因は相槌F1の低下。same と session に有意差なし。
2. **継続/完了の二値分離は 0.65 前後で頭打ち。** 文脈・手法・適応強さのどれを変えても 0.63〜0.66。→ **モデルの表現力ではなく、ラベル品質（LLM 付与 F1 0.805）やタスク定義の曖昧さが上限を規定している可能性が高い。**
3. **適応量を制御すれば ASR を保ったまま適応できる**（本実験群の最大の成果）。Adapter s≤0.2 で CER 23.3（凍結と同一）のまま macro-F1 改善。s=0.4 が最良（macro 0.729 / CER 23.9）。

### 最良条件のまとめ（同一話者）
| 手法 | 最良N | macro-F1 | 二値分離 | CER |
|---|---|---|---|---|
| 凍結 | 1 | 0.722 | 0.650 | 23.3 |
| LoRA | 0 | 0.725 | 0.658 | 23.8 |
| **Adapter (s=0.4)** | 0 | **0.729** | 0.656 | 23.9 |

詳細な数値は `docs/peft_report.md` に全表あり。

## 2.5 音声とテキストの併用（2026-09）

**評価の枠組みが変わった。** 2 節までは発話単位・判定時点固定。ここからは
**フレーム単位ダンプ + 停止規則**（`local/turntaking/frame_rules.py`）で測る。
1 区間あたり約 90 時点の確率を共通格子（0.05 秒刻み・上限 3.0 秒）に載せ、
「音声区間検出が発話末 + 0.25 秒で発火する」制約の下で同じ規則を各モデルに当てる。
指標は 応答ミス / 誤割り込み / 完了の遅延 / macro-F1 / 短縮。
**2 節の数値とは直接比較できない。**

### クラス別内訳（融合の利得はどこから来るか）

| 音声の重み | macro-F1 | 継続F1 | 完了F1 | 相槌F1 |
|---|---|---|---|---|
| 0.00（テキストのみ） | 0.7327 | 0.564 | 0.704 | 0.930 |

| 1.00（音声のみ） | 0.7306 | 0.531 | 0.740 | 0.921 |

**利得はほぼ全部「継続」から来る。** 継続F1 +0.037 に対し、完了F1 はむしろ悪化し、
相槌F1 は横ばい。テキストは「まだ言い終えていない」を見抜くのが得意で、
「言い終えた」の判定には貢献せず、相槌には無関係。統語的に未完成な文は見れば分かる。
macro-F1 の山は重み 0.30〜0.70 で 0.7406〜0.7439 と平坦なので、
対話システムの設計方針（遮りたくない／応答遅れを避けたい）で自由に選べる。

### 確定した結論

1. **表現の段階で統合する共同学習は失敗する（0.7143、音声のみより −0.016）。**
   BERT の 768 次元表現をヘッドに渡して一緒に学習すると、train tag_acc は
   1 エポック目で 0.760、以降 0.78 台で 30 エポック以上動かない（音声のみは
   0.665 から着実に上昇）。発話全体の認識結果は「完了しているか」をほぼ直接
   教えるため、ヘッドが最初からそこに依存し音声側が育たない。しかも因果性の
   制約でこの表現は発話末以降しか使えないので、発話途中は育っていない音声側
   だけで判定することになる。悪化は**誤割り込み**に集中（0.244 → 0.276）し、
   応答ミスはほぼ同じ（0.248 → 0.247）。この読みと整合する。
2. **macro-F1 を決めているのは結合の仕方ではなく動作点。** 下記の改良はすべて
   単一重み 0.7429 を超えなかった。
3. **動作点は dev から eval へ転移しにくい。** dev では学習した結合器が単一重みを
   0.017 上回ったが、eval では −0.002 に反転。単一重みで dev が選んだ 0.45 に対し
   eval 最良は 0.60。自由度の低い結合の方が頑健。

### N-best（唯一効いた改良）

1-best の認識結果 1 本ではなく、**5 候補それぞれに BERT を通し、ASR スコアの
softmax を重みに確率を平均する**。候補の選択はしない（BERT は誤った認識結果にも
自信を持つため）。`local/turntaking/nbest_fusion.py`。
温度と重みは dev で選択（温度 4.0 / 音声 0.50）。

| 条件 | macro-F1 | 1-best 比 |
|---|---|---|
| 1-best 融合 | 0.7429 | — |
| **N-best スコア重み付き平均（dev 選択）** | **0.7461** | **+0.0032** |
| N-best 単純平均 | 0.7465 | +0.0036 |
| オラクル N-best（正解に最も近い候補・到達不能） | 0.7498 | +0.0069 |

- **2 位以下に 1 位より良い候補がある発話は 42.4%。** オラクルで選べば CER 平均が
  0.351 → 0.215 に下がる。候補は全 23,444 件で 5 通りとも異なる（重複なし）。
- **候補数は 5 で十分。10 に増やしても実測は動かない（0.7461 → 0.7463）。**
  オラクルは 0.7498 → 0.7538 と +0.0040 伸びるのに、回収率が 46% → 27% に落ちる。
  オラクル CER を押し下げるのは 6〜10 位だが、それらは ASR スコアが低く softmax の
  重みが付かない。温度 4.0 という平坦な重みでもそうなる。
  **スコアという物差しでは下位候補の良し悪しを見分けられない。**
  デコード時間が倍になるだけなので 5 候補を使うこと。
- dev でも +0.0050 で、eval の +0.0032 と符号が一致する（結合器のような反転は無い）。
- eval 上で温度を掃引すると 1.0 で 0.7476 だが、dev が選ぶのは 4.0。
  **報告すべきは dev 選択の 0.7461。**
- 温度 0.5〜4.0 で 0.7460〜0.7476 と平坦なので、選択に敏感ではない。

**なぜこれだけ効いたか。** 効かなかった 4 手法はすべて「既にある 1 本の認識結果を
どう使うか」の工夫で、動作点が支配的な問題では曲線上を移動するだけに終わる。
N-best だけが**入力の情報量そのものを増やしている**。門番（捨てる）の
オラクル上限が +0.0025 だったのに対し、N-best（増やす）は +0.0069 ある。

### 効かなかった手法（すべて記録）

| 手法 | macro-F1 | なぜ効かないか |
|---|---|---|
| 1-best 単一重み（N-best 前の最良） | 0.7429 | — |
| MBR 選択（候補どうしの合意で 1 本選ぶ） | 0.7437（5 候補）/ 0.7424（10 候補） | 1 位と違う候補を 30.8% で選んでおり機能はしている。だが**選択は情報を捨てる操作**。平均なら認識の揺れがそのまま判断の揺れになり動作点に反映されるのに、1 本に絞るとそれが消える。候補を増やすと誤選択の機会が増えてさらに悪化 |
| BERT 確信度に連動した重み | 0.7421 | BERT は誤った認識結果にも自信を持つ。実質「重みを平均的に下げる」だけで曲線上を移動している |
| 学習する結合器（対数確率 6 次元 → 3 クラス） | 0.7180 | 対数尤度で学習すると動作点が macro-F1 と噛み合わない。重み無しは完了側、クラス重み付きは継続側に振り切れる |
| 同上 ＋ 動作点調整（dev で補正 2 自由度） | 0.7411〜0.7417 | 動作点だけで 0.7180 → 0.7411（+0.023）動く。動作点が支配的という仮説の確認。ただし追加の自由度に見返りは無い |
| 門番（代理量で認識の信頼度を判定） | 0.7420〜0.7429 | 代理量（1 秒あたり文字数・2-gram 反復率）と CER の順位相関が 0.117 とほぼ無相関。dev は「全部通す」閾値を選ぶ |
| 門番（正解 CER・到達不能） | 0.7454 | **上限が +0.0025 しかない。門番という筋自体に余地が無い** |

### 効き方の法則（この問題に固有）

| 系統 | 手法 | 結果 |
|---|---|---|
| **増やす・均す** | N-best スコア重み付き平均 | 0.7461 ○ |
| | N-best 単純平均 | 0.7465 ○ |
| **選ぶ・捨てる** | 門番（認識信頼度で捨てる） | 0.7429 × |
| | BERT 確信度連動 | 0.7421 × |
| | MBR 選択 | 0.7437 × |
| **結合をいじる** | 学習する結合器（＋動作点調整） | 0.7411〜0.7417 × |

**不確かさを保ったまま下流に渡す手法だけが効く。** 認識が揺れている発話では、
揺れていること自体が情報。どれか 1 本に決めるとその情報が消える。
macro-F1 を動作点が支配するこの問題では、不確かさが動作点の調整に効いている
という読みが最も整合的。新しい手法を考えるときは、この軸で先に分類すること。

|---|---|---|---|---|---|
| 0（完全一致） | 8,700 | 0.371 | 0.7738 | 0.8047 | 0.8128 |
| 0.0〜0.2 | 3,134 | 0.134 | 0.6666 | 0.6903 | 0.7753 |
| 0.2〜0.5 | 6,157 | 0.263 | 0.7304 | 0.7372 | 0.7782 |

高 CER 帯では融合の利得が消える（CER>1.0 では音声のみより悪い）。
**ただしこれを根拠に「2 割で損している」と読んではいけない。** macro-F1 は
帯ごとに分解できない。実際、高 CER 帯を音声のみに戻す門番の上限は +0.0025。
天井との差 +0.040 は「捨てる」「加減する」では回収できず、
認識結果そのものを良くするしかない。

### 注意点（落とし穴）

- **フレームダンプの上限は 3.0 秒。** 判定時点で発話末を過ぎているのは
  **88.2% だけ**で、残り 11.8%（長い発話）は判定時点が発話の途中に来る。
  そこで認識結果を混ぜると**未来が漏れる**。`frame_fusion.fuse()` は
  `grid >= 発話長` のフレームだけ混ぜることで防いでいる。自前で
  「判定時点の確率を取り出してから混ぜる」と漏れる（実際に一度踏んで
  0.7429 が 0.7502 に化けた）。
- **N-best を出すには `nbest` を 2 箇所に書く。** `myconf/decode_*_nbest5.yaml` の
  トップレベル（`asr_inference` 側の切り詰め）と `transducer_conf` の中
  （`BeamSearchTransducer` 自前の `nbest`。`**transducer_conf` でしか届かない）。
  **片方だけでも警告もエラーも出ず、1 本しか返らないまま完走する**（31 分無駄にした）。
  本番前に 20 発話で候補が 5 本返ることを確認すること。
- **`asr.sh` は `1best_recog` しか集約しない**（`asr.sh:2024-2026`）。
  2〜N 番目は `logdir/output.*/` に残る。`local/turntaking/merge_nbest.sh` で連結する。
- **ビームが N 本返さない発話がある**（eval で 8〜20 件）。欠けた候補を確率 0 の
  ベクトルとして扱うと平均もオラクルも狂う。有効性マスクで除外すること。
- **`tt_use_dec`（デコーダ状態をヘッドへ）をフレーム単位に持ち込まないこと。**
  `evaluate_multitask.py:143` が**発話全体の仮説トークン列**を渡しており、
  マスクが無い。フレーム単位で評価すると未来が漏れて見かけ上よい数字が出る。
  `exp/asr_20260807-...-dec-...` は 17 エポックで打ち切り（最良 6 エポック）の
  未完成な実験でもある。

## 2.7 融合のテキスト側を詰めた記録（2026-09-30）— 打ち止め

§2.6 の 0.7537 から先を、**テキスト側（BERT）だけで**伸ばそうとした試み。
**8 本の BERT と 2 つのアイデアで 1 つも 0.7537 を超えられなかった。**
同じことを繰り返さないために、やったことと数値を残す。

### 出発点の疑問

融合のテキスト側 `exp/text_bert_asr` は**旧 Stage1（CER 23.3）の認識結果で学習**されている
（`local/turntaking/text_ceiling.py` の `--train_text` は「ASR 仮説で学習＝条件をそろえる」
という意図の引数）。Stage1 を替えたので、BERT は学習時より綺麗なテキストを受け取っている。
**条件を揃え直せば伸びるはず**と考えた。

### 結果（すべて 融合 macro-F1・dev 選択・eval 23,444 区間）

| 条件 | 学習テキスト | macro-F1 |
|---|---|---|
| **元の `exp/text_bert_asr`** | 旧仮説・**学習記録なし** | **0.7537** ← 最良 |
| 新仮説で学習 4 本 | 新（CER 20.7） | 0.7495 / 0.7495 / 0.7516 / 0.7507（平均 0.7504・**SD 0.001**） |
| 旧仮説で再学習 2 本 | 旧（CER 23.3）・今のスクリプト | 0.7520 / 0.7511（平均 0.7516） |
| 旧＋新 連結 2 本 | 197,135 × 2 = 394,270 | 0.7520 / 0.7516（平均 0.7518） |
| 新 4 本のアンサンブル | | 0.7527 |
| 連結 2 本のアンサンブル | | 0.7530 |
| 元の旧 ＋ 再学習 2 本のアンサンブル | | 0.7532 |

### 確定したこと

1. **「条件を揃える」は効かない。** 新仮説で学習すると平均 0.7504 で、元の 0.7537 より
   **0.0033 低い**。新 4 本のばらつきは SD 0.001 しかないので、これは揺らぎではない。
2. **その差の大半は学習テキストではない。** 旧仮説で「今のスクリプト」で再学習しても
   0.7516 止まり。内訳は **学習テキスト起因が +0.0012（約 1 SD）／説明できない分が +0.0021**。
   元の `text_bert_asr` の優位は、**記録されていない学習条件の差**が主。
   → 「汚いテキストで学習した方が頑健」という説明は**成り立たない**（当初そう解釈したが誤り）。
3. **データ量 2 倍・ノイズ混合は無効。** 連結（0.7518）は旧仮説単独（0.7516）と同値。
4. **アンサンブルは単体最良を超えない。** 0.7527〜0.7532 で、いずれも 0.7537 未満。
   弱いモデルを混ぜると薄まる。
5. **BERT 単体の性能と融合後の性能は一致しない。** 新仮説 BERT は発話単位 3 クラスで
   ASR テキスト 0.7391 → 0.7468、正解テキスト 0.7813 → 0.7859 と**明確に上**なのに、
   融合では下がる（`tt_analysis/text_bert_*.json`）。

### 残った宿題

**元の `exp/text_bert_asr` の +0.0021 が再現できない。** 学習に使った引数の記録が無い。
`text_ceiling.py` に**乱数シードの制御が無い**ため、そもそも同一条件の再現ができない。
→ 今後 BERT を学習するときは **seed を固定できるようにしてから**回すこと。
現状は `exp/text_bert_asr` を「動く最良の資産」として保存し、消さないこと。

### 早期確定についての構造的な制約（重要）

融合はテキストを**発話末以降のフレームにしか混ぜない**（因果性の制約。発話途中では
その発話の認識結果が存在しない）。したがって:

- **「区間検出まで待つ」= 発話末以降 → テキストが効く → 0.7537**
- **発話中に確定する早期確定 → 音声モデル単独の質で決まる**

**早さを伸ばしたいならテキスト側をいくら磨いても無意味で、音声側を良くするしかない。**
現状の早さ（音声=blk42 / テキスト=旧BERT）:

| 規則 | macro-F1 | 短縮 |
|---|---|---|
| 区間検出まで待つ | 0.7537 | — |
| 完了τ=0.82 | 0.7529 | 0.172 秒 |
| 完了τ=0.70 | 0.7485 | 0.537 秒 |

旧の融合 1-best は τ=0.70 で 0.7410・0.587 秒だったので、**同程度の短縮で精度 +0.0075**。

## 3. コードの地図

### モデル本体: `espnet2/asr/espnet_model_turntaking_xfmr.py`
- `class BottleneckAdapter` … Adapter 本体。`down(d→r)→ReLU→up(r→d)`、up は零初期化。
  - `use_ln`（既定False）: 入力LayerNorm。**True にすると壊れる**（実測CER46.7）。旧実装再現用。
  - `max_ratio`（既定0=制限なし）: 補正の大きさを `≤ max_ratio × ||入力||` に射影。**Adapter の暴走を止める鍵。**
- `class TurnTakingXfmrHead` … Self-Attention 1層 + MLP。`head_type="selfattn"`（既定）or `"transformer"`。
- `class TurnTakingXfmrASRModel`
  - `tt_adapt`: `"none"`（完全凍結）/ `"lora"` / `"adapter"`。
    - `"none"`: エンコーダを `no_grad`+`eval` で呼ぶ（ASR完全不変）。
    - それ以外: エンコーダを**勾配ありで**呼ぶ（追加パラメータに勾配を流す）。BNだけ eval 固定。
  - `_install_encoder_adapters(...)`: Adapter を **forward hook** で FFN 出力に加算（`tt_adapter_targets` で挿入先、既定は主FFN 12箇所）。**モジュール差し替えではなく hook** ← パラメータ名を変えず Stage1 重みを読めるようにするため。
  - LoRA は abs_task 側の `create_adapter` が担当（config の `use_adapter: true`）。

### 過去ベクトル: `local/extract_past_vectors.py`
- 各発話を凍結エンコーダで符号化 → **有効フレームで max pooling** → uvec_max (256次元)。
- 直前N発話（same or session）を積んで `(n, 256)` 行列 = `past_vec`。`--uvec_cache` で N によらず再利用。

### 設定ファイル: `myconf/`
- `train_asr_turntaking_xfmr.yaml` … 凍結 Stage2 のベース。`init_param` は `exp/asr_PUREASR_TAG/...`（run スクリプトが sed で置換）。
- `train_asr_turntaking_xfmr_lora.yaml` … LoRA（`use_adapter: true`, `adapter: lora`, `adapter_conf: {rank:8, alpha:8, target_modules:[linear_q, linear_v]}`）。
- `train_asr_turntaking_xfmr_adapter.yaml` … Adapter（`tt_adapt: adapter`, `tt_adapter_bottleneck:32`, `tt_adapter_ln:false`, `tt_adapter_max_ratio:0.4`, `tt_adapter_targets:[feed_forward]`）。

## 5. 次にやりたいバリエーション（本題）

**結論として過去発話は効かないので、今後は「過去発話 N を振る」より「モデル/学習側の変更を N=0 で試す」方が費用対効果が高い。** 以下、優先度つき。各項目に「狙い」「実装の勘所」「開始手順」を記す。

### 5.1 【推奨・最優先】ラベル/タスク側の検証

> **2026-09-30 実施** → `docs/label_quality_gold1000.md`。人手正解 1000 件（605 件が使用可）で、
> 音声モデルの二値一致は 人手 0.697 / LLM ラベル 0.648。LLM ラベル自体が人手と 0.742。
> 0.805 は「完了」クラスの F1 で、継続 F1 は 0.60。
**狙い**: 二値分離0.65の壁が「モデルの限界」か「ラベルの限界」かを切り分ける。これが最重要の未解決問題。
- **人手ラベルとの一致率を継続/完了に絞って分析。** LLM(Qwen3-8B)付与ラベルの F1 は 0.805。モデルの0.65がラベルのノイズ由来なら、モデルをいじっても無駄。
- 具体案: (a) 人手正解1000件（既にLLM評価で作成済み）に対する Stage2 モデルの一致を測る。(b) モデルが間違える例を人が見て「ラベルが妥当か」を確認。
- 実装はほぼ分析スクリプトのみ。学習不要。**時間対効果が最大。**

### 5.2 Pooling の変更（過去発話の要約方法）
**狙い**: 過去発話が効かない原因の一つが「max pooling で潰しすぎ」の可能性。
- 現状: `local/extract_past_vectors.py` の `utt_maxvec` が `eo[0,:n].max(dim=0).values`（max pooling）。
- 変更案: **attention pooling**（学習可能な重みで加重平均）/ mean pooling / [CLS]的な学習トークン。
- 勘所: max→mean は `extract_past_vectors.py` の1行変更で済むが、**attention pooling は「過去ベクトルを事前計算」する枠組みと相性が悪い**（poolingが学習対象になるとエンコード時に確定できない）。その場合は past_vec を事前計算せず、**ヘッド側で過去発話フレーム列を受け取って pooling する**構造変更が必要。→ モデル改造が要る中規模タスク。
- ただし「過去発話自体が有害」という結論があるので、**優先度は中**（pooling を変えても過去が効くようにならない可能性）。

### 5.3 ヘッドの変更
**狙い**: Self-Attention 1層が弱い/強すぎる可能性。
- `tt_head_type: transformer`（FFN+残差+LN付き、`tt_xfmr_layers` で層数）に切替可能。config を変えるだけ。
- 層数・ヘッド数（`tt_xfmr_layers`, `tt_xfmr_heads`）の掃引。
- 勘所: 実装済みなので config 変更のみ。**低コスト。** ただし N=0 で試すこと（過去は効かないので）。

### 5.4 PEFT のハイパラ探索
**狙い**: Adapter/LoRA の設定は最小限しか探索していない。
- **Adapter**: bottleneck（32固定→8/16/64）、挿入先（`tt_adapter_targets` に `feed_forward_macaron` や self-attn 出力を追加）、s の細分化（0.3/0.5）。
- **LoRA**: rank（8→4/16）、target_modules（Q,V→Q,K,V,O）、alpha。
- 勘所: すべて config 変更で済む。**Adapter の bottleneck を 16 にすると学習パラメータが LoRA と厳密に一致**（現状 Adapter 200K vs LoRA 98K の適応部分差を揃えられる → より公平な比較）。

### 5.5 PEFT の種類を増やす
**狙い**: Serial Adapter 以外の PEFT。
- **Parallel Adapter**（元の層と並列に Adapter、同じ入力を受ける）: 現状は Serial（FFN出力を入力）。hook を pre-forward にして入力を受け、モジュール出力に足す形へ。
- **Prefix Tuning / (IA)³** など。
- 勘所: 中〜大規模の実装。まず 5.3/5.4 の低コスト案を尽くしてから。

### 5.6 早期確定（TEASER 等）
**狙い**: 発話の途中で `<完了>` を確定し応答遅延を抑える（要件②）。**これは精度改善とは別軸の課題。**
- 準備資料あり: `local/turntaking/teaser.py`, `docs/turntaking_teaser_method.md`（過去に作成、未実行の可能性）。
- 勘所: 学習済みモデルの「発話プレフィックスごとの予測確率」を使う後処理。モデル再学習は不要。精度と早さのトレードオフを描く。

## 6. よくある落とし穴（過去に踏んだ）

1. **同名 exp の上書き。** 同じ日に再実行すると `asr_<今日>-...` が衝突。旧版は `mv ..._oldXXX` で退避。
2. **旧 Adapter (LN版/24箇所) の残骸。** `exp/asr_20260721-...adapter...` は CER 46.7 の失敗版。`_oldLN` に退避済みだが、集計スクリプトが `ls | tail -1` で拾うので**日付の新しい正しい版が選ばれるか確認**すること。
3. **`freeze_param` は勾配を止めるが BatchNorm の running 統計は止めない。** → モデルの `train()` override で対処済み。新しい適応手法を足す時もこの原則を壊さない。
4. **Adapter の暴走。** タグ損失しか無いのでエンコーダを動かせるようにすると補正が青天井（CER 46.7）。**必ず `max_ratio` で上限をかける。**
5. **loralib が必要。** `pip install loralib`（導入済み）。ESPnet 組み込みの houlsby adapter は **S3PRL 専用**で本構成では使えない（→ Adapter を自前実装した理由）。
6. **評価の past_vec 取り違え。** N によって `past_vec_<variant>.scp` が変わる。`run_xfmr.sh` が学習前に正しい variant を `past_vec.scp` にコピーしている。評価は `eval_xfmr_series.sh` が variant を組み立てるので、**手動で past_vec を指定する時は N と scope と suffix を一致させる。**
7. **バリデータ(dataviz)の node が古い。** サーバの node は v6 で ES2016 が動かない。パレット検証は `references/palette.md` の検証済み値をそのまま使う。
