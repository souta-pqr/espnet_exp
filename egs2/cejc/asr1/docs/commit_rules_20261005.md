# 早期確定の規則を dev で選び直す（2026-10-05）

対象: SESSION_HANDOFF_20260930 §3 の 3 番。スクリプト `local/turntaking/commit_rules.py`（CPU のみ）。

## 背景：これまでの「最良 τ」は eval で選んでいた

`frame_fusion.py` の「基準を崩さず最も早い完了 τ」（例: 融合で τ=0.82・0.172 秒短縮）は
**eval 上で選んでいた**。融合の重みは dev で選んでいたが、τ は評価データで選んでいたので楽観的。
動作点は dev から eval へ転移しにくい（HANDOFF §2.5）ので、規則も dev で選んで eval で報告する。

選択基準は従来どおり「応答ミスも誤割り込みも基準（区間検出まで待つ）+0.005 以内で、完了の遅延が最小」。
eval でもこの条件が守れたかを ○/× で併記する。

## 規則の族

どれも「完了」だけを早期確定し、それ以外は区間検出まで待つ。

| 族 | 内容 |
|---|---|
| 完了τ | p(完了) ≥ τ（従来） |
| 余裕δ | p(完了) − p(継続) ≥ δ |
| ＋持続 k | k フレーム（0.05 秒刻み）連続で満たしたら確定（k=1,2,3） |
| ＋ゲート g | 発話開始から g 秒は確定しない（0〜1.0 秒） |

## 確定したこと

1. **単純な完了τを dev で選ぶと、eval では条件を破りやすい（6 件中 5 件で ×）。** dev はわずかに攻めた τ を選ぶ。
   従来報告の「τ=0.82 で 0.172 秒短縮」などは eval で選んだ楽観値だった。
2. **「余裕δ＋持続 3 フレーム」は転移に頑健。** 融合ではどのモデルでも dev 選択がそのまま eval で ○。
   1 フレームだけの確率の跳ねで確定しないため、dev と eval で動作点がずれにくいと読める。
   **今後、早期確定の規則はこの族から dev で選ぶこと。**
3. **規則を工夫しても短縮はほとんど増えない。** 持続・ゲート・余裕のどれを足しても、eval で選んだ上限は
   従来の完了τと同程度（B 融合で 0.225 → 0.227 秒）。**早さはモデル（音声側）で決まる**という既知の結論を補強する。
   **注意：この表の短縮量でモデルどうしを比べてはいけない。** 基準が「各モデル自身の区間検出まで待つ」なので、
   基準が高い B ほど条件が厳しくなる（短縮は 元 0.249 秒 > B 0.226 秒になるが、B が遅いわけではない）。
   モデル間は同じ閾値で比べる。完了τ=0.70 で 元 0.7485 / 0.537 秒 → **B 0.7526 / 0.645 秒**と、B は精度も早さも上。
4. **測っている「誤割り込み」の約半分はラベル誤りの可能性がある。** 人手正解のある学習外区間（81 件）で、
   選んだ規則が LLM ラベル≠完了 なのに完了と確定した区間（21〜28 件）のうち、人手では完了が 43〜54%。
   件数が少ないので目安だが、LLM ラベルで測ると早期確定のコストを過大に見積もっていることになる
   （`docs/label_quality_gold1000.md`：LLM の継続ラベルは人手 F1 0.60 と弱い）。
