# 発話区間末検出の精度と早さを詰める

作成日: 2026-09-28

## 行ったこと

- 以下の二つに対して行った
    - 発話区間末検出精度を上げる（応答ミスを減らす）
    - 早期確定の精度を上げる（応答遅延を減らす）
- 評価指標の変更
    - macro-F1 から「失敗の種類（応答ミス・誤割り込み・応答の遅延）」に変えた．
- 分かったこと
    - **完了クラスだけに閾値を置くと，応答が 0.125 秒早くなる**（3 シードで確認）．
    - 精度は 0.72 前後で頭打ち．原因はモデルではなく**正解ラベルの不確かさ**．
    - 発話後の無音を学習に入れても，効果がない．

---

## 1. 背景

現在の対話システムで課題が二つある．

| 課題 | 内容 |
| --- | --- |
| 応答ミス | ユーザはもう言い終えているのに，システムが「まだ続く」と判断して応答しない |
| 応答遅延 | 言い終えたかの判断が遅く，応答を始めるのが遅れる．無言の間が空く |
- どちらも「相手が言い終えたか」を正しく・早く判定できれば解決する．
- 関連研究
    - 音声区間検出 (VAD): 有音検出．考えながらの沈黙と，言い終えた沈黙を区別できない．
    - 音声活動予測 (VAP): 次に誰が話すかのタイミングを予測する．発話内容の意味は見ていない．
- → 本研究では，**発話内容の意味に基づいて「伝えたいことを言い終えたか」を判定する**．

---

## 2. タスク

3 つの発話区間末タグを判定する．

| 発話区間末タグ | 意味 | 例 |
| --- | --- | --- |
| 完了 | 伝えたいことを言い終えた | 「明日はちょっと無理なんだよね」→ 応答してよい |
| 継続 | まだ言い終えていない | 同じ文でも，続けて「だから来週に…」と言うなら継続 |
| 相槌 | 聞き手からの短い発話 | 「うん」「へえ」 |
- **文の形だけでは発話区間末タグは定まらない**
- データ：日本語日常会話コーパス（CEJC）
    - 学習 80.5 時間，評価 9.9 時間（23,444 区間：完了 10,906・継続 6,255・相槌 6,283）．
    - タグは大規模言語モデル（Qwen3-8B）が書き起こしとタイミングから付与した．
    - 人手正解 1,000 件に対する付与精度は F1 0.805．**正解ラベル自体に約 2 割の誤りがある**．

## 4. 評価指標の変更

- これまでは macro-F1（3 クラスを対等に扱う平均）で比べていた．
    - しかし継続を当てても，システムは聞き続けるだけで行動は変わらない．
    - 研究の動機（応答ミス・応答遅延）と対応していない．
- そのため，**失敗の種類**で測ることにした．
- 応答ミスと誤割り込みは，一方を下げればもう一方が上がる．
- 「**どちらの失敗も基準より悪化させずに，どれだけ早く応答できるか**」．

## 5. 発話区間末検出精度の良くするために行ったこと

| 試したこと | 結果 |
| --- | --- |
| 過去発話を入れ方の変更 | 圧縮せず全部渡しても「過去なし」と差なし |
| 過去発話の数を 1 → 5 に増やす | 同一手法で完全に同値 |
| エンコーダの部分適応（LoRA） | わずかに改善するが，認識精度が劣化 |
| 学習率スケジュールの修正 | **改善（最大の効果）** |
| 損失関数の変更・ヘッドの大型化 | 効かない or 悪化 |
| 別話者の過去発話を入れる | macro-F1 は上がるが，継続を完了と間違うようなミスが増加． |
- **精度（macro-F1）は 0.72 前後で頭打ち**になった．

### 試した過去発話の入れ方  (6 手法)

#### 1. max，attention pooling

- max pooling
    
    例) 次元 0 の値が [0.2, 0.9, 0.1 …] なら → 0.9．これを256次元分．
    
- attention pooling
    
    例) attention 重みが [0.01, 0.30, 0.02, …] (合計 1) なら→ 0.01 * v1 + 0.30 * v2 + …
    

#### 2. 圧縮しない

- 過去フレーム列をそのままヘッドに渡す
    - 圧縮情報が聞かなかったとき，「圧縮の仕方が悪いのか」，「過去にそもそも情報がない」かを知りたかった．
    - 当たり前だが，ヘッドの計算量は膨大．((204 + 46) の 2乗) / (46 の 2乗) = 29 (倍)

#### 3. conv

参考文献: Rae et al., "Compressive Transformers," ICLR 2020

- 過去発話を c フレームずつのブロックに切り，各ブロックを kernel = stride = c の conv1d で 1本にする
    
    ```jsx
    入力  [f1 … f26][f27 … f52][f53 … f78] … （8 ブロック、端は 0 埋め）
            ↓Conv1d    ↓Conv1d    ↓Conv1d
    出力     s1         s2         s3      …  s8      → (8, 256)
    ```
    

#### 4. query

参考文献: Lee et al., "Set Transformer," ICML 2019／Jaegle et al., "Perceiver," ICML 2021

- 学習したquery を M 本持ち，それぞれが過去フレーム列に cross-attention して情報を出力する．
    
    ```jsx
    学習クエリ q1 … q8（各 256 次元・学習で決まる）
        q1 ──注意──▶ 204 フレーム → 重み付き和 → s1
        q2 ──注意──▶ 204 フレーム → 重み付き和 → s2
          …                                     …
        q8 ──注意──▶ 204 フレーム → 重み付き和 → s8     → (8, 256)
    ```
    

#### 5. topk

参考文献: Rae et al., ICLR 2020 の "most-used"／ Xu et al., "Show, Attend and Tell," ICML 2015

- 各フレームに Linear でスコアを付け，上位 8 フレームだけを残す
    
    ```jsx
    スコア  f1:0.1  f2:0.8  f3:0.2 … f97:0.9 … f204:0.3
              ↓ 上位 8 個を選ぶ
    選択    f2, f17, f41, f66, f97, f120, f158, f190
              ↓ 時系列順に並べ直す（選択で順序が崩れるため）
    出力    [f2, f17, f41, f66, f97, f120, f158, f190] → (8, 256)
              ただし各フレームに sigmoid(スコア) を掛ける
    ```
    

### 頭打ちの原因は，モデルではなく正解ラベル

- 正解ラベルは言語モデルが付けたもので，人手正解に対する精度は F1 0.805．
- 同じ入力を別の言語モデルに与えて付け直すと，**判断が分かれる区間が 3 分の 1** あった．
- 2 つの言語モデルの判断が一致する区間だけで測ると，モデルの性能は大きく上がる．
- → 残りの誤りの多くは，**ラベル自体が定まらない区間**から来ている．

### 別の検出方式と比較した結果

- 「音声認識してからテキスト分類器に通す」方式と比べた．
    - 実際の認識結果を使った方式より，本手法が上．
    - 正解の書き起こしを使った理想的な方式と，ほぼ同等．
- → 認識誤りで劣化しないことが，音声から直接判定する設計の根拠になる．

## 6. 早期確定

- 発話を最後まで聞かずに判定を確定できれば，その分だけ応答が早くなる．
- ただし早く切るほど情報が減り，誤りやすくなる．

### 完了クラスだけに閾値を置くことに意味がある

- 早く確定して意味があるのは「完了」だけ．継続を早く確定しても，聞き続けるだけ．
- ところが従来の規則は 3 クラスすべてに早期確定を許しており，継続・相槌の誤りまで前倒ししていた．
- そこで，**完了クラスだけに閾値を置き，それ以外は区間検出まで待つ**規則にした．

| seed | 規則 | 応答ミス | 誤割り込み | 完了の遅延 | 早くなる量 |
| --- | --- | --- | --- | --- | --- |
| 30 | 基準（区間検出まで待つ） | 0.251 | 0.260 | −0.135 秒 | — |
| 30 | **完了τ=0.76** | **0.246** | 0.264 | −0.256 秒 | **0.121 秒** |
| 1 | 基準 | 0.280 | 0.232 | −0.135 秒 | — |
| 1 | **完了τ=0.76** | **0.272** | 0.237 | −0.263 秒 | **0.128 秒** |
| 2 | 基準 | 0.273 | 0.241 | −0.135 秒 | — |
| 2 | **完了τ=0.74** | **0.266** | 0.246 | −0.260 秒 | **0.125 秒** |
- τ は開発データ（train_dev）で選び，評価データ（eval）で測った．
- 応答ミスも誤割り込みも基準より悪くせずに，少しだが早く応答できる．
- 従来の推奨規則（全クラス共通の閾値 ＋ 経過時間の下限）と比べ，3 シードすべてで
    - 早く確定し，
    - macro-F1 も高く，
    - 応答ミスは基準より低い．
- 調整するパラメータが 1 つだけなのも利点．

### 検証：無音を学習に入れても効果はなかった

| 条件 | 応答ミス（基準） | 早くなる量 | 判定 |
| --- | --- | --- | --- |
| 既存モデル | 0.269 | 0.117 秒 | — |
| 無音込み（条件を 4 つ変えた） | 0.298 | 0.114 秒 | 悪化に見えた |
| 無音込み（差を無音だけに絞った） | 0.269 | 0.125 秒 | **差なし**． |
- 結論: 性能に変化はない．
    - 設定が単純な既存モデルを使い続けるのがよいと思われる

## 7. まとめ

### 応答ミスについて

- 0.72 前後で頭打ち．原因はモデルではなく正解ラベルの不確かさ．
- 過去発話の文脈は，どう渡しても効果が小さい．
- 学習率スケジュールの修正がいちばん効いた．
- 音声から直接判定する設計は，認識を経由する方式より強い．

### 早期確定について

- 学習時にも発話を途中で切って見せると，途中の判定が安定する．
- 完了クラスだけに閾値を置くと，0.125 秒早くなる（3 シードで確認）．
- 発話後の無音を学習に入れても効果はない．
- 評価条件（無音・区間検出）を明記しないと，結論を誤る．

### 教訓

- 指標は研究の動機に合わせる．
- 条件を一度に複数変えると，否定的な結果の原因が特定できない．
- 乱数の種を変えた再現性の確認を，結論を出す前に必ず行う．

## 8. 次に行うこと

1. 精度の軸：正解ラベルの質を上げる．
    - 複数の言語モデルの判断を統合する方法が候補．
2. 早さの軸：フレーム単位で連続に判定する構成なら，まだ改善の余地がありうる．
